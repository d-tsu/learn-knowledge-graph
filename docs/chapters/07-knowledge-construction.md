# 第7章：文書・データ・コードから知識を構築する

更新日：2026-10-11。執筆とレビューの状況は[README](../../README.md)で確認できる。

## この章の到達点

原本の構造を保ちながら知識を抽出し、対象を照合して公開する流れを説明できるようになる。パーサ・静的解析・LLMを使い分け、条件・否定・例外を失った候補を見つける。

## 読めるテキストにするだけでは足りない

図書室の利用規約に、次の表があるとする。教材用の架空の例である。

| 利用者区分 | 同時貸出上限 |
|---|---|
| 一般利用者 | 3冊 |
| 職員 | 5冊 |

表の下には「館内閲覧資料は冊数にかかわらず館外へ貸し出さない」とある。数値だけを抽出すると、誰の上限なのか分からない。脚注を落とすと、館内閲覧資料も上限以内なら貸せるように読めてしまう。

この表は列や行に意味がある**構造化データ**である。説明文は、内容を文章として読む**非構造化データ**として扱うことが多い。ただし、文章にも見出し・箇条書き・表の配置がある。抽出前にすべてを一続きの文字列へ変えると、その手がかりを失う。

## 原本から公開までを分ける

**パイプライン**は、入力をいくつかの処理段階へ順に渡す仕組みである。知識構築では、抽出した候補を直ちに確定データへ入れず、照合・検査・レビューを挟む。

```mermaid
flowchart LR
  A[原本と版を登録] --> B[表・節・注記を保つ]
  B --> C[主張の候補を抽出]
  C --> D[対象を照合]
  D --> E[条件と根拠を確認]
  E --> F[承認した版を公開]
```

原本を残せば、誤った候補から元の表へ戻れる。公開版を分ければ、未確認の抽出結果が利用者の回答へ混ざることを防げる。これは本資料で採る構築手順であり、特定製品に必須の構成ではない。

| 入力 | 抽出後も残す位置情報 | 失いやすい情報 |
|---|---|---|
| Excel | ブック・シート・セル範囲と見出し | 結合セル、注記が適用される行 |
| Word | 文書版・節・表番号と原本 | 図中の条件、本文と注記の対応 |
| Markdown | 文書ID・版・節と原文 | 見出しの適用範囲、コードと説明の区別 |
| API仕様 | 版・操作ID・項目への位置 | 別文書にある業務条件 |
| コード | コミット・ファイル・シンボル | 動的な呼出先、外部設定の影響 |

Markdown化は差分や節の参照を扱いやすくするが、変換前後の表と注記の対応を確認する必要がある。文字認識を使った場合は、例えば「3」が「8」になっていないかも点検する。

## パーサ・静的解析・LLMの分担

**パーサ**は、決められた構文に従って入力を読み取るプログラムである。表の列やAPI仕様の操作IDなど、構造が決まっている部分を安定して取り出すために使う。例えば[OpenAPI 3.1.1のOperation Object](https://spec.openapis.org/oas/v3.1.1.html#operation-object)には、操作を識別する `operationId` を記述できる。

**静的解析**は、コードを実行せずに構造や値の流れを調べる方法である。関数の呼出しや、入力がどの比較へ渡るかを調べられる。解析範囲やライブラリのモデルによって取得できる関係は変わる。動的に決まる呼出先をすべて確定できるとは限らない。[CodeQLのデータフロー解析](https://codeql.github.com/docs/writing-codeql-queries/about-data-flow-analysis/)

LLMは、自然言語の条件を整理したり、別名の候補を挙げたりするために使える。もっともらしい補完も行うため、出力には根拠位置と未確認事項を求める。

| 処理 | 向く入力・仕事 | その結果だけでは確定しないこと |
|---|---|---|
| パーサ | セル、JSONの項目、定義された構文 | 二つの部署の「利用者」が同じ意味か |
| 静的解析 | 呼出し、変数の代入、比較に届く値 | コードの条件が業務上正しいか |
| LLM | 文章の候補抽出、言い換え、照合候補 | 候補が原文と一致し、公開してよいか |

構造化された項目をLLMに読み直させる必要はない。パーサの結果と文章からの候補を同じモデルへ集め、確認が必要な箇所を絞る。

## 条件・否定・例外を一組で残す

冒頭の表から、一般利用者の上限を次のような候補へ整理できる。

| 項目 | 候補の内容 |
|---|---|
| 誰に適用するか | この図書室の一般利用者 |
| 何を数えるか | 同時に借りている本の冊数 |
| 上限 | 3冊 |
| 組み合わせて確認する規則 | 館内閲覧資料の館外貸出禁止 |
| 根拠 | 利用規約の該当表と表直下の注記 |
| 確認が必要なこと | 規約の適用日、冊数を確認するタイミング |

原文に確認のタイミングが書かれていなければ、抽出処理で「確定直前」と補ってはいけない。第6章のモデルに項目があることと、この原本に値があることは別である。

「職員は5冊まで」という行も残す。一般利用者の行へ混ぜると、全利用者の上限が5冊に変わってしまう。否定文は「館内閲覧資料」と「館外へ貸し出さない」を一組にして保持する。禁止される操作と対象を落とさないためである。

## IDがない対象を照合する

原本にIDがなくても、構築側で文書や断片に安定したIDを付けられる。文書IDと原本の位置、内容のハッシュ、文書の版は別に保存する。ハッシュは内容が変わると変わるので、改名や改訂をまたぐ対象IDの代わりにはしない。

二つの台帳の「田中」を同じ利用者へ統合するには、名前以外の根拠が必要になる。会員番号の対応や所属図書室などを確認する。根拠が足りない場合は別々の対象として保持し、同一候補という状態を付ける。

概念の表記ゆれには、第2章の確認済みの別名表を使える。原文の「貸出資料」を残しながら、登録名「貸出用資料」の概念ID K-01へ対応付ける。言葉が同じ概念を指すことと、二つの記録が同じ人を指すことは、それぞれ根拠を確認する。

照合処理には「確定」「別対象」「保留」を用意する。誤統合は、片方の貸出をもう一方の人の冊数へ加える原因になる。候補を保留できる設計が、無理な統合を防ぐ。

## 検査・レビュー・公開

公開前の機械検査では、IDの重複、参照先の欠落、必要な出典、関係の向きなどを調べる。原文の意味を正しく読んだかは、原文と候補を並べて確認する。

確認用の少数の例には、通常の文章だけでなく、表の注記・否定・例外・同名の別対象を含める。例えば冒頭の教材なら、抽出された規則が「一般3冊」「職員5冊」「館内閲覧資料は館外貸出禁止」の三つを保ち、未記載のタイミングを未確認にしているかを点検する。

承認者・抽出器の版・対象原本・承認した候補を記録してから公開する。再取り込みした候補が以前と違えば、変更箇所をレビューへ戻す。更新・削除と公開後の管理は次章で扱う。

## 復習

- 表を一続きのテキストにすると、どんな条件を失いやすいか。
- パーサ、静的解析、LLMは何を分担できるか。
- 同一候補を保留することが必要なのはなぜか。

## 演習と解答例

### 演習1：脚注の条件

規約の表に「一般利用者3冊、職員5冊」とあり、脚注に「未返却の延滞資料がある利用者への新規貸出は停止する」と書かれている。LLMは「職員は5冊まで借りられる」とだけ出力した。

公開する前に何を直し、何を原本で確認すべきだろうか。

解答例：職員の上限5冊と、延滞がある利用者の新規貸出停止を両方残す。脚注が職員にも適用されるか、延滞の定義や確認する日時がどこに書かれているかを原本で確認する。5冊以内という条件だけで、職員の申込みを許可する候補にしてはいけない。

### 演習2：同名の照合

図書室AとBの台帳にそれぞれ「田中」がいる。会員番号も連絡先も取得できていない。処理は、同名という理由で一人へ統合しようとしている。

どの状態で保持し、何を確認すればよいだろうか。

解答例：図書室ごとに別の対象として残し、同一候補は保留する。担当者に対象の対応を確認できる資料を求める。名前の一致だけでは別々の人の貸出が混ざるおそれがある。確認資料が得られなければ、統合しないまま収録範囲を説明する。
