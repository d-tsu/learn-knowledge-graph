# 第11章：編集・構築・推論・検証のツール

更新日：2026-10-11。執筆とレビューの状況は[README](../../README.md)で確認できる。

## この章の到達点

編集、抽出、問い合わせ、推論、制約検証を担当するツールを区別できるようになる。小さな例で入力と出力を確かめ、必要な処理だけを組み合わせる。

## ツール名より、入出力を先に決める

「オントロジーを作るツール」を一つ選んでも、原文からの抽出と意味の確認、運用中の更新まで自動的に決まるわけではない。例えば第9章の例には、Turtleを読み込む処理、SPARQLを実行する処理、SHACLを検査する処理がある。それぞれに入力と期待する結果を用意する。

| 作業 | 入力 → 出力 | 代表的な道具 |
|---|---|---|
| 定義の編集 | クラス・関係の定義 → オントロジーのファイル | Protégé |
| 文書からの抽出 | 原文 → 対象・関係の候補 | パーサ、LLM Graph Builderなど |
| RDFの処理 | RDFファイル → 読込み・変換・問い合わせ結果 | RDFLib、Apache Jena |
| 推論 | 公理と事実 → 帰結や整合性の結果 | HermiT、ELK、OWL-RLなど |
| 制約検証 | データと制約 → 適合・違反の報告 | pySHACL、JenaのSHACL処理 |
| 描画・分析 | グラフ → 図や経路・統計 | Graphviz、NetworkXなど |

この表の製品は、作業の対応を理解する例である。検証器が違反を報告しても、原文の読み違いを修正する担当者は別に必要になる。

## Protégéで定義を編集する

**Protégé**は、OWLオントロジーを編集する環境である。例えば「印刷書籍」「印刷資料」というクラスと下位クラス関係を編集し、定義をファイルとして保存する。ローカル向けのProtégé Desktopと、共同編集向けのWebProtégéがある。[Protégé公式サイト](https://protege.stanford.edu/)

画面上でクラスの階層を並べられることと、定義が目的に合うことは別に確認する。第4章のように、含めたい例と含めたくない例を使って範囲を点検する。推論器を接続する場合は、編集した公理をその推論器が扱えるかも確認する。

共同編集では、誰の提案を誰が承認し、どの版を公開するかを決める。編集画面のスクリーンショットだけでなく、定義のファイルと変更理由を残すと再確認しやすい。

## RDFをプログラムで処理する

**RDFLib**はPythonからRDFを読み書きし、SPARQLなどを扱うライブラリである。第9章の実習では、別の構文を同じグラフへ読み込み、内容を比較した。手順をプログラムへ残すと、同じ版のデータへ繰り返し適用できる。[RDFLib公式リポジトリ](https://github.com/RDFLib/rdflib)

例えば文書から抽出した候補を読み込み、IDを対応付け、制約検査後に公開用ファイルへ書き出す処理を組める。原本の位置や確認状態を保存する設計は、ライブラリ側ではなく第6〜8章の方針で決める。

Javaを使う構成ならApache JenaにもRDF処理や問い合わせ・推論・SHACLの部品がある。言語の習熟、既存の運用、必要な構文と推論範囲を合わせて選ぶ。[Apache Jena Documentation](https://jena.apache.org/documentation/)

## 抽出ツールの結果を候補として扱う

**LLM Graph Builder**は、LLMを使って非構造化データからグラフを構築するツールの例である。対応する入力や接続先は公式の対象版を確認する。[Neo4j Labs LLM Graph Builder](https://github.com/neo4j-labs/llm-graph-builder)

第7章の表を入力した場合には、「一般利用者3冊」「職員5冊」「館内閲覧資料の館外貸出禁止」が残るかを確かめる。図が生成されたことだけを成功にせず、注記・適用条件・原文位置を点検する。元の文書にない関係や、似た名前の誤統合も確認する。

自動抽出の出力形式が自分のモデルと違う場合は、変換と検査を挟む。出力の関係名をそのまま正式な語彙にするかは、モデルの管理者が判断する。

## 推論器と検証器を選ぶ

推論器には、扱える公理と実行する処理の範囲がある。例えばELKはOWL 2 ELの一部を扱う推論器であり、OWL-RLはRDFLib上でルールによる帰結の追加を行う実装である。HermiTもOWL推論器の一例になる。名称だけで相互に同じ結果を保証すると考えず、利用する公理と処理を照合する。[ELK](https://github.com/liveontologies/elk-reasoner)、[OWL-RL](https://github.com/RDFLib/OWL-RL)、[HermiT](https://github.com/phillord/hermit-reasoner)

選定時の小例には「期待する帰結」「導かれては困る帰結」「矛盾する設定」を含める。結果が出ない場合には、公理の不足と、そのツールの対応範囲を分けて調べる。公理を黙って無視した結果を、定義全体による判断と呼ばない。

例えば第9章の `owl:inverseOf` はOWL 2 ELの範囲外なので、ELKに同じ導出を任せる構成にはしない。第9章の実習ではOWL-RL 7.1.4を使い、L-08の借りた人がU-03という記録から、U-03には貸出L-08があるという帰結を確認する。このように、使う公理と期待する結果を一組にして対応範囲を調べる。[OWL 2 ELの表現範囲](https://www.w3.org/TR/owl2-profiles/#OWL_2_EL)

SHACL検証器には**pySHACL**などがある。第9章では `inference='none'` とし、記載したデータに借りた人のIRIが一つあるかを調べた。推論による補完を使う場合は、補完前と補完後のどちらを検査したいかを決める。[pySHACL公式リポジトリ](https://github.com/RDFLib/pySHACL)

検査報告には対象ノード、違反した条件、検査したデータの版を残す。「不適合」の一語だけでは、担当者がどこを修正すべきか分からない。

## 可視化・探索・分析

**可視化**では、グラフを読める図にする。**探索**では、条件を変えながら関係や原文を調べる。**グラフ分析**では、経路やつながりの数などを計算する。例えば、多数の要件と結び付くAPIを見つけ、重点的に見直す候補にできる。

Graphvizは図の配置と描画に、NetworkXはプログラムからのグラフ操作や分析に使える。[Graphviz Documentation](https://graphviz.org/documentation/)、[NetworkX Documentation](https://networkx.org/documentation/stable/)。つながりが多いことは業務上の重要性を直接証明しないため、分析値が何を数えたかを説明する。

図には、問いに必要な対象と関係だけを出す。すべてを一枚に並べると、線が多くても判断材料は増えない。原文へ戻るリンクと、対象を絞る条件を用意する方が有効な場合もある。

## 最小の処理列を組む

図書室の小例なら、次の処理列から始められる。LLMも専用DBも必須ではない。

1. 担当者が原本と対応するTurtleを手作業で作る。
2. RDFLibで読み込み、SPARQLの期待結果を確かめる。
3. pySHACLで必要な記載を検査する。
4. 原文との照合後、承認した版を公開する。

分類の推論が必要になった段階で、対応する推論器を追加する。文書量が増えた段階で抽出処理を追加し、手作業の結果を比較基準にする。追加した部品ごとに、誤りの調べ方と保守する担当者を決める。

## 復習

- オントロジーの編集、推論、制約検証では、入出力がどう違うか。
- 抽出ツールで図ができた後、何を確認するか。
- グラフ分析の値を業務上の重要性として使うには、何が必要か。

## 演習と解答例

### 演習1：欠落を見つけたい

担当者は、貸出の借りた人が未記載のデータを見つけたい。OWL推論器でクラス階層を計算するだけで目的を達成できるだろうか。必要な入力と出力を挙げよう。

解答例：記載の検査条件と対象データを用意し、SHACL検証器などで調べる。出力には未記載の貸出IDと違反した条件が必要になる。クラス階層の計算結果は、データに相手のIDが書かれていることを保証しない。補完を使うかどうかも検査設定に残す。

### 演習2：自動抽出を追加する

手作業で確認した規約が五つある。LLMによる抽出を追加する場合、どの結果を比較し、どの作業を残すか。

解答例：確認済みの対象・規則・適用条件・原文位置と抽出候補を比較する。通常文だけでなく注記・否定・例外も含める。候補の照合、原文との意味の確認、承認の仕事は残す。抽出量が増えたことと、正確な知識が増えたことを分けて評価する。
