# 評価と段階的な実証

## 何を改善したいかを固定する

最初の仮説は「複数の設計に分散する前提条件を結ぶことで、結合・システムテスト案の欠落を減らせる」である。グラフのノード数、見た目、生成テスト件数だけでは効果を判断しない。

## 比較実験の案

| 条件 | エージェントに与える情報 | 比較目的 |
|---|---|---|
| A | 単一の対象設計 | 他文書の情報がない場合の欠落を測る |
| B | 全文検索・ベクトル検索で取得した関連記述 | 通常の検索で十分かを見る |
| C | 人が整備したID・対応表と原文 | グラフDBなしの構造化の効果を見る |
| D | 根拠・条件付きグラフと原文 | 関係探索の追加価値を見る |

Aだけに勝ってもグラフ固有の効果とは言えない。B・Cとの比較が重要である。モデル、プロンプト、文書版、出力形式、取得情報量または費用の条件をそろえ、情報量を増やした効果と表現形式の効果を分ける。少数回の生成で結論を出さず、複数回の揺れも記録する。

## 評価単位と指標

| 指標 | 測定方法 |
|---|---|
| 主張の適合率 | 正しい抽出主張数 / 評価した抽出主張数 |
| 主張の再現率 | 抽出できた必須主張数 / 正解集合の必須主張数 |
| 前提条件充足率 | 正しく記述された必須前提数 / 必須前提総数 |
| 根拠の妥当性 | 原文がその主張を支えているかをレビュー |
| 期待結果の正確性 | 仕様の許可・拒否・状態変化と一致するか |
| 実行可能率 | 環境・データ・手順がそろって実行できるケースの割合 |
| 不足検出 | 未定義事項を推測で埋めず報告できたか |
| 更新追従 | 仕様変更後に旧知識や旧期待結果が残らないか |
| 総コスト | 抽出・実行費用に加え、レビュー・維持・修正の時間 |

正解集合は、人が複数文書を確認して作り、モデル調整に使う題材と評価用題材を分ける。分母がゼロの指標はN/Aとし、率だけでなく件数も残す。架空の正解集合での成績と実業務での効果は区別する。

## 段階的な進め方

1. **学習**：基礎章とミニ例を読み、用語・役割を説明できる状態にする。
2. **手作業の小モデル**：少数の設計から、概念・根拠・問いを整理する。DBは不要。
3. **問い合わせの比較**：同じ問いを対応表、PG、RDFで表現する。学習用の小データから始める。
4. **抽出の比較**：ルール抽出とLLM抽出を分け、条件・否定・出典の精度を測る。
5. **テスト案生成**：前提、準備手順、実行、期待結果、根拠、不足事項を出力する。
6. **実行と変更検証**：テスト環境で動かし、仕様変更時の再生成・再検証まで確かめる。

現時点で完了しているのは学習資料の初版作成。実証、DB導入、製品選定は未実施。

## 学習後の発展テーマ

状態機械とモデルベーステスト、制約充足によるデータ生成、境界値・組合せテスト、Datalog等の規則、時間・版を含む知識管理、設計とコードの差分検出を候補とする。これらはグラフの周辺技術であり、本初版では詳細な実装は扱わない。

## 復習・演習

「グラフ化したらテストが増えた」を改善と呼べない理由を説明する。重複、誤った期待結果、実行不能な前提が増えていないかが判断のポイント。
